## 1. Application Overview

A Permit to Work (PTW) application for LV Electrical work, built in Oracle APEX 24.2.
Based on the BGIS/GWS physical permit form. Supports offline working, geolocation
capture, digital signatures, and a role-based workflow.

### Workflow Steps (Pages)
| Page | Name | APEX Alias |
|------|------|------------|
| 1 | Dashboard | HOME |
| 2 | Site & Work Details | SITE-WORK-DETAILS |
| 3 | Control Measures & PPE | CONTROL-MEASURES |
| 4 | Equipment Isolation | EQUIPMENT-ISOLATION |
| 5 | Authorisation & Acceptance | AUTHORISATION-ACCEPTANCE |
| 6 | Change History | (history) |
| 7 | Location | (map) |
| 8 | User Management | (admin) |
| 9 | Start Permit (active) | (start) |

### Workflow Status Values (workflow_status column)
- `IN_PROGRESS` — permit being filled out
- `AUTHORISED` — page 5 signed off
- `SUSPENDED` — permit suspended
- `CANCELLED` — permit cancelled
- `CLOSED` — permit closed/cleared

### Pages are Read-Only when workflow_status != 'IN_PROGRESS'
Each page uses: `p_read_only_when_type = 'VAL_OF_ITEM_IN_COND_NOT_EQ_COND2'`

## 3. DATE FORMAT RULES — CRITICAL

**Always use this format mask everywhere, consistently:**
```
DD-MON-YYYY HH24:MI
```

**Never use seconds (`HH24:MI:SS`) — this causes ORA-01821.**

| Location | Correct Code |
|----------|-------------|
| SELECT into page item | `TO_CHAR(accept_datetime, 'DD-MON-YYYY HH24:MI')` |
| DML save to database | `TO_DATE(:P5_ACCEPT_DATETIME, 'DD-MON-YYYY HH24:MI')` |
| Page item default | `SELECT TO_CHAR(SYSDATE,'DD-MON-YYYY HH24:MI') FROM dual` |
| Exception handlers | `TO_CHAR(SYSDATE,'DD-MON-YYYY HH24:MI')` — **must match** |
| APEX item Appearance > Format Mask | **Leave blank** — only works on Date Picker, not Text Field |

**Date columns stored as DATE type in the database:**
`accept_datetime`, `auth_from_datetime`, `auth_to_datetime`,
`clear_datetime`, `cancel_datetime`, `completion_date`

## 4. JAVASCRIPT ARCHITECTURE RULES — CRITICAL

### Page 0 Limitations
**Page 0 does NOT have:**
- `Function and Global Variable Declaration` property
- `File URLs` property (for referencing JS files per-page)

**Page 0 DOES have:**
- Hidden items: `P0_LATITUDE`, `P0_LONGITUDE`
- These are global session state items used across all pages

### Reusable JavaScript Functions — USE STATIC APPLICATION FILES
Any JavaScript function needed on more than one page **must** go in a
Static Application File, not in a Dynamic Action or page-level JS.

**How to add a static JS file:**
1. Create the `.js` file locally
2. `Shared Components → Files → Static Application Files → Upload`
3. Reference on Page 0 via: `Page Properties → JavaScript → File URLs`
   - Use: `#APP_FILES#filename#MIN#.js`
4. Because it's on Page 0, it loads on every page automatically

**Current Static JS Files:**
| File | Purpose | Referenced On |
|------|---------|---------------|
| `offline-storage#MIN#.js` | Offline/IndexedDB storage | Pages 1,2,3,4,5 individually |
| `ptw-utils.js` | Geolocation + submit helper | Page 0 (global) |

### DO NOT use these approaches for global JS functions:
- ❌ Page 0 Dynamic Action → Execute JavaScript Code (function scope only, not global)
- ❌ Repeating the same function on multiple pages
- ❌ Inline JS in HTML regions

## 5. GEOLOCATION PATTERN — CRITICAL

### The Problem with `getCurrentPosition`
Browser geolocation is **asynchronous**. Never follow a geolocation call with
an immediate page submit — the coordinates will be empty when the form submits.

### The Correct Pattern
Use `captureLocationThenSubmit(request)` from `ptw-utils.js`.
This captures GPS coordinates **then** submits inside the callback.

```javascript
// In ptw-utils.js
function captureLocationThenSubmit(request, callback) {
    function doSubmit() {
        if (typeof callback === 'function') { callback(request); }
        else { apex.page.submit(request); }
    }
    if (!navigator.geolocation) { doSubmit(); return; }
    navigator.geolocation.getCurrentPosition(
        function(position) {
            apex.item('P0_LATITUDE').setValue(position.coords.latitude);
            apex.item('P0_LONGITUDE').setValue(position.coords.longitude);
            doSubmit();
        },
        function(error) {
            apex.item('P0_LATITUDE').setValue('');
            apex.item('P0_LONGITUDE').setValue('');
            doSubmit(); // always submit even if location fails
        },
        { enableHighAccuracy: true, timeout: 8000, maximumAge: 0 }
    );
}
```

### Button Setup for Pages Needing Geolocation (Pages 2, 3, 4, 5)

Buttons must be `DEFINED_BY_DA` (not Submit Page) so a DA can intercept
the click, capture location, then submit.

**Button Static IDs:**
| Page | Button | Static ID |
|------|--------|-----------|
| 2 | SAVE_DRAFT | BTN_SAVE_DRAFT_P2 |
| 2 | NEXT_STEP | BTN_NEXT_STEP_P2 |
| 3 | SAVE_DRAFT | BTN_SAVE_DRAFT_P3 |
| 3 | NEXT_STEP | BTN_NEXT_STEP_P3 |
| 4 | SAVE_DRAFT | BTN_SAVE_DRAFT_P4 |
| 4 | NEXT_STEP | BTN_NEXT_STEP_P4 |
| 5 | SAVE_DRAFT | BTN_SAVE_DRAFT (already set) |

**DA Pattern for Pages 2, 3, 4:**
```
Event:           Click
Selection Type:  jQuery Selector
jQuery Selector: #BTN_SAVE_DRAFT_Pn, #BTN_NEXT_STEP_Pn

True Action: Execute JavaScript Code
Code:
    var request = $(this.triggeringElement).attr('id').indexOf('SAVE_DRAFT') > -1
                  ? 'SAVE_DRAFT' : 'NEXT_STEP';
    captureLocationThenSubmit(request);
```

**Page 5 — modify existing SAVE_DRAFT DA, Action 30:**

## 8. SIGNATURES

- Captured using HTML5 Canvas signature pads
- Stored as BLOB in database (`auth_person_signature`, `accept_person_signature`, etc.)
- Loaded back as base64 data URLs: `data:image/png;base64,...`
- Page items: `P5_AUTH_SIGNATURE_DATA`, `P5_ACCEPT_SIGNATURE_DATA` (hidden)
- JS functions: `initSignaturePads()`, `saveSignatures()`, `loadSignature()`
- `saveSignatures()` is called on `apexbeforepagesubmit` event
- Signatures are converted to/from BLOB using `apex_web_service.blob2clobbase64`
  and `apex_web_service.clobbase642blob`

## 10. KNOWN ISSUES & FIXES APPLIED

### ORA-01821 — Date Format Not Recognised (FIXED)
**Cause:** Exception handler in Page 5 Before Header process used `HH25:MI`
(invalid Oracle format — does not exist).
**Fix:** Changed to `HH24:MI` throughout. All format masks must be consistent.

### apex.da.initDaEventList is not a function (FIXED)
**Cause:** Dynamic Action on Page 0 with invalid/empty jQuery selector binding.
**Fix:** Never use Page 0 DAs for defining global JS functions.
Use Static Application Files instead.

### captureLocationThenSubmit is not defined (FIXED)
**Cause:** JS function placed in a Page 0 DA — DA scope is not global.
**Fix:** Function moved to `ptw-utils.js` Static Application File,
referenced via Page 0 → JavaScript → File URLs.

### Geolocation always saving NULL coordinates (FIXED)
**Cause:** `getCurrentPosition` is async — old DA submitted the page
before the GPS callback fired.
**Fix:** `captureLocationThenSubmit()` submits the page inside the
success/error callbacks, guaranteeing coordinates are set first.

## 12. CODING STANDARDS

- ### YOU MUST ALWAYS WORK SYSTEMATICALLY

### PL/SQL
- Always use `ptw_pro.` prefix for all table references
- Exception handlers must use the **same** date format masks as main code
- Always include `WHEN OTHERS` with `SQLERRM` in save processes
- Use `NVL(V('APP_USER'), USER)` for audit columns
- Use `CURRENT_TIMESTAMP` for `modified_date`, `created_date`

### APEX
- Before Header processes must have server-side condition
  `Item is NOT NULL` on the primary key item (e.g. P5_PERMIT_ID)
  to prevent errors when navigating directly to a page
- Buttons that need geolocation → `DEFINED_BY_DA` + Static ID
- Buttons that are simple navigations → `REDIRECT_PAGE`
- Buttons that are simple submits with no geolocation → `SUBMIT`

### JavaScript
- Reusable functions → Static Application File
- Page-specific functions → Page `Function and Global Variable Declaration`
- Never put global functions in Dynamic Actions

## 14. PERMIT PHOTOS

### Table
- `ptw_pro.ptw_lv_permit_photos` — child table, FK to `ptw_pro.ptw_lv_permits` ON DELETE CASCADE
- Sequence: `ptw_pro.ptw_lv_photo_seq`
- Index: `ptw_pro.idx_ptw_lv_photos_permit` on `permit_id`

### Upload mechanism
- File read client-side using FileReader.readAsDataURL()
- Base64 stripped of data URL header in JavaScript before sending
- Sent as f01 array (30KB chunks) in a SINGLE apex.server.process call
- PL/SQL reassembles f01 array into CLOB, converts to BLOB via
  apex_web_service.clobbase642blob() — same pattern as Page 5 signatures
- DO NOT use apex_application_temp_files for AJAX uploads —
  temp files are only populated on full page submit, not AJAX calls
- DO NOT use g_x01-g_x10 for binary data — hard limit of 32KB each

### Application Processes
| Process              | Point         | Purpose                          |
|----------------------|---------------|----------------------------------|
| `UPLOAD_PERMIT_PHOTO`| Ajax Callback | Receives f01 array, inserts BLOB |
| `GET_PERMIT_PHOTOS`  | Ajax Callback | Returns JSON array for gallery   |
| `DELETE_PERMIT_PHOTO`| Ajax Callback | Deletes — uploader or ADMIN only |

### Photo serving — Page 20 (Photo Download)
- Blank page, alias: `photo-download`
- Single hidden item: `P20_PHOTO_ID`, Value Protected: NO (Unrestricted)
  ← Value Protected MUST be No, otherwise SSP blocks the URL parameter
- Before Header process streams BLOB via wpg_docload.download_file()
- Must re-raise apex_application.e_stop_apex_engine in WHEN OTHERS
- URL generated via: apex_page.get_url(p_page=>20, p_items=>'P20_PHOTO_ID', p_values=>photo_id)
- DO NOT use apex_util.prepare_url with f?p= syntax in friendly URL apps
  — generates wrong checksum format, causes SSP_VIOLATION2

### Page 4 Components
- `P4_PHOTO_FILE` — File Browse, capture="environment" (opens camera on mobile)
- `P4_PHOTO_CAPTION` — optional caption
- `ADD_PHOTO` button — Defined by DA, condition: P4_PERMIT_ID NOT NULL
- `#ptw-photo-gallery` div in Permit Photos static region

### JS functions (Page 4 Function Declaration)
- `loadPermitPhotos(permitId)` — calls GET_PERMIT_PHOTOS, renders grid
- `deletePtwPhoto(photoId, permitId)` — confirm + DELETE_PERMIT_PHOTO

### Offline behaviour
- Upload disabled when !navigator.onLine — shown as error message
- Gallery load fails gracefully with "Could not load photos" when offline

### How Oracle APEX Works
- Oracle APEX provides all the tools you need to build apps in a single, extensible platform, which runs as a part of Oracle Database.

- Oracle APEX uses a simple 3-tier architecture where requests are sent from the browser, through a web server, to the database. All processing, data manipulation and business logic is executed in the database. This architecture guarantees zero latency data access, top performance, and scalability, out of the box.

- Oracle APEX installs with your Oracle database and consists of data in tables and PL/SQL code. Whether you run the APEX development environment or run an application built using APEX, the process is the same. Your browser sends a URL request that is translated into the appropriate APEX PL/SQL call. After the database processes the PL/SQL, the results are relayed back to your browser as HTML. This cycle happens each time you either request or submit a page.

- APEX does not use a dedicated database connection. Instead, each request is made through a new database session, consuming minimal CPU resources. Application session state is managed in the database tables by the APEX engine.

- Behind the scenes, the APEX engine renders and processes pages. The APEX engine also performs these tasks:

- Session state management

- Authentication services

- Authorization services

- Page flow control

- Validation processing
